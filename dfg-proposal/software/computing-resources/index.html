Why 1,000,000 CPU-core-hours?

A transparent feasibility estimate for atomistic sampling, numerical validation, mesoscale interaction, continuum finite elements and separately calibrated material decohesion over 36 months.

Proposal versus planning scenario: The DFG proposal specifies a provisional envelope of 1.0 million CPU-core-hours and up to 10 TB working/project storage. Its original allocation is 150k preparation + 600k ARTn/NEB + 150k AQS/validation + 100k mesoscale/kinetic. The subdivided last 100k used below—60k mesoscale + 25k continuum + 15k conditional cohesive fracture—is an explicit proposed revision for transparent planning, not the original allocation. It does not change the overall core-hour request. All job counts and runtimes are planning assumptions, not measured benchmarks.

View executable budget calculation

Core-hour arithmetic

CPU-core-hours = number of independent jobs × allocated CPU cores/job × actual wall hours/job. A node with 32 allocated cores running for 7.5 hours incurs 240 core-hours (whether each core is fully utilized or not); queued time is excluded. These estimates assume requested cores are billed as allocated.

Crucial distinction: 1 million core-hours ≠ 1 million elapsed hours. For example, a fully utilized 1,000-core allocation would complete one million core-hours in 1,000 elapsed hours (about 41.7 days), ignoring queue delays, varying workload parallelism and utilization. Realistic science requires many different jobs, independent replicate ensembles and sequential validation checkpoints.

Why each category is scientifically necessary

150k · Preparation

Quench reproducible independently prepared glasses across sizes and preparation histories. Sampling must separate sample-to-sample physics from one exceptionally prepared configuration.

600k · ARTn / NEB

Rate-predictive transfer is dominated by adequate coverage of rare low-barrier channels, independent restarts, uniqueness checks, pathway refinement and stress sensitivity; one saddle count histogram cannot prove completeness.

150k · AQS / validation

Matched stress-driven deformation and Hessian-instability tests on the same glass preparation, plus independent structures and loading directions for falsifiable ARTn–AQS overlap.

60k · Mesoscale

Compare independent rate activation, elastically interacting events and evolving post-transition networks using identical calibration, with temperature/rate and finite-size sweeps.

25k · Continuum FEM

Solve RVE boundary-value problems and test mesh independence, finite-strain work-conjugate stress/tangent, Hill–Mandel energy balance and representative-volume convergence.

15k · Conditional fracture

Only once separation data exist: run controlled cohesive-traction or phase-field benchmarks, mixed-mode and mesh-size checks, and independent crack-initiation/path tests. Not an unconditional promise of predictive fracture.

Continuum jobs may vary substantially by mesh (degrees of freedom), number of Newton iterations, constitutive update cost, and solver scaling. The 125×16×12.5 h and 75×16×12.5 h values are initial sample workload budgets, not verified solve times. If pilot timings show that finite-strain 3D RVE or phase-field jobs cannot fit, the project must reduce case counts, simplify geometry, request justified additional resources, or keep fracture conditional—not quietly claim these allocations suffice.

The 10 TB subdivision is a storage-management scenario; it is not a measured dataset volume, and institutional archival limits and policies require confirmation. The original proposal only specifies the provisional aggregate up to 10 TB.

Measured benchmarks required before production runs

The proposal calls for pilot profiling during months 1–3. Actual cores × walltime, memory per rank, storage per event, strong/weak scaling and I/O performance will be logged for representative preparation, ARTn, NEB, AQS and mesoscale jobs, with continuum FE and cohesive pilot jobs added to the revised planning scenario.

Core-hours and uncertainty

Report median and high-quantile runtime per task, convergence of unique low-barrier event rates with extra searches, number of independent replicas and sensitivity to missed channels. Set checkpoints for budget reallocation.

What is not justified yet

Specific GPU-hours, a guaranteed 3D crack-prediction campaign, a fixed node type, instantaneous strong scaling, or an awarded institutional allocation. No GPU resources are specified in the current CPU-core-hour envelope.

Research integrity: An HPC resource estimate is a testable plan, not a measured performance result. The proposed breakdown is reproducible using estimate.py. Pilot profiling must replace illustrative runtimes and justify any change to the originally stated DFG resource categories.
